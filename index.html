Problem statement 1 · AI surface defect detection

A defect born upstream travels the whole route. This finds it, in your browser, in about thirty milliseconds.

Crazing starts at reheat or coiling. Inclusions start at the caster. Rolled-in scale starts at the descaler. By the time a coil is graded, melting, rolling, annealing and pickling have all been paid for — and on 304 the nickel is 8–10% of the mass, so a downgraded tonne destroys several times what a tonne of commodity carbon steel does. Manual inspection samples; it cannot cover the whole surface of a strip moving at 300 m/min.

This page is the detector itself, not a description of one. Drop in a steel image below and a 3.0 M-parameter YOLOv8n runs on the WASM backend of ONNX Runtime, in the tab, with no server anywhere. The numbers it prints are calibrated probabilities, and the decode it runs has been checked detection-for-detection against the Python model. Thirty milliseconds is the forward pass measured inside the page itself — single-threaded WASM, warm-up excluded. Your machine is not this machine, so the timing panel below measures it on yours rather than repeating this number. site/verify/parity_browser.json → summary.session_run_ms

The three things that had to be exactly right

Half-pixel sample centres, src = (dst + 0.5) × scale − 0.5. The 11-bit fixed-point weights OpenCV actually uses, applied in integer arithmetic, not a float approximation of them. And the fact that cv2.resize on a uint8 image returns uint8, so the network never sees the float interpolant. Getting the second one wrong — doing the interpolation in float64 and rounding at the end — disagreed with cv2 on 12% of bytes instead of 0.1%, moved one box by 19 px, and flipped an NMS tie so a detection vanished.

Scale, do not pad

Within one window the frame is scaled into the 256×256 input rather than letterboxed, because that is what the project measured: lossless padding loses 0.024–0.052 mAP50 to ordinary bilinear scaling at the same tensor size, on 8 of 8 configurations, and nearest-neighbour magnification — also lossless — is the worst of five arms. For a square source, which every NEU-DET frame is, scaling and letterboxing are the same operation. That is what makes this comparison a valid check on the resize. A frame that is not square is not squashed either: it is cut into square windows first, so the scale stays uniform on both axes. Padding and squashing are both avoided, by different means. reports/input_pipeline_decision.md section 3, reports/input_pipeline_probe.json

The one gap that is Node's, not the browser's

Node has no libjpeg, so the harness decodes JPEGs with a pure-JS decoder whose IDCT differs from the libjpeg-turbo one OpenCV uses — mean 0.075 of 255 per byte. Let that in and the worst box moves 9.5 px. Hold the source pixels constant and it is 0.14 px, which is the number in the table. Browsers decode JPEG with libjpeg-turbo, the same library OpenCV uses, so this gap is a property of the harness rather than of the page. Both runs are kept, in parity_js.json and parity_js_jpegjs.json, precisely so the residual is attributed instead of hand-waved.

Two decisions that mattered more than the architecture

256 px, not 640

Test mAP50 runs 0.7524 / 0.7286 / 0.6230 / 0.4843 / 0.3438 at 256 / 320 / 416 / 512 / 640 px. A detector can only regress a box at the magnification it was trained at, so inheriting the framework's generic 640 would have run this model at less than half its accuracy. A dedicated 150-epoch 640 px training run was then done anyway to check the constant honestly: its own best is 0.7338, which ties the shipped 0.7524 inside the ±0.0254 bootstrap band. reports/model_study.json → runs; reports/resolution_study.json

Nano, not small

The 3.7× larger yolov8s loses. At the training size the gap is +0.0688 mAP50 to nano, 95% CI [+0.0309, +0.0990], nano winning in 99.95% of 2,000 bootstrap resamples; at deployment size +0.0181, CI [−0.0084, +0.0424]. The larger model overfits: its classification-loss generalisation gap is +0.267 against nano's −0.061. 3.012 M against 11.138 M parameters, 1.312 against 4.584 GFLOPs at 256 px. reports/model_study.json → bootstrap, training_history, checkpoints

The strongest result: the model was asked to look at clean steel, and it failed

Every number above is in-domain. The interesting question for a mill is what the detector does on steel with nothing wrong with it, from a different line and a different camera. So that was measured on 505 held-out clean Severstal frames (4,040 tiles) plus 191 masked-defective frames (546 tiles) — and the shipped model, which has never seen clean steel, flags 93.7% of the clean frames as defective at a cross-domain ROC AUC of 0.608. That is indistinguishable from a coin toss.

What fixed it

1,190 certified-clean training crops, joint training on real target-domain positives and negatives, with the NEU-DET class indices left untouched at 0–5 and four Severstal classes appended at 6–9. Not a threshold change, not a post-hoc filter: the backbone learns that clean steel is clean. The lesson generalises and is the one to carry into a deployment plan — budget a joint fine-tune with real negatives for every new grade and every new camera, because the features do not transfer on their own.

Why it is not the default yet

The joint checkpoint scores better on both axes and it is still not shipped, deliberately. The Severstal release publishes a numeric mask value 1–4 and nothing else: no defect name, no metallurgical description, no grading rule. So the severity tier that drives a coil's release decision cannot be set for those four classes without inventing metallurgy, and inventing it is the one thing this project will not do. They sit at the neutral middle tier with an explicit admission in place of a root cause, and the quality department owns the number. reports/severstal_dataset.md; src/inference.py SEVERSTAL_TIER

You can see the failure in the demo above

Click the strip 2048×1000 roll mark chip. It is a GC10 line-scan frame of carbon steel with a roll mark on it — a defect family this six-class head was never trained on. Across three tiled passes it returns rolled-in_scale at raw 0.355 and inclusion at 0.270. The weld-line frame returns patches at 0.526 and 0.308 and scratches at 0.369. Every one of those five calls is confidently the wrong name, because the right name is not in this head's vocabulary — and none of them is a refusal. That is the 93.7% number in miniature: a detector with no concept of “something else” answers anyway. The joint checkpoint in the table above and the out-of-scope gate in the console are the two fixes, and neither is wired into this page. site/verify/parity_browser.json → out_of_domain (regenerated with the tiled path)

An out-of-scope gate exists too

A separate guard rejects input that is not steel at all: zero false rejections across 3,200 genuine steel frames (1,440 + 180 + 180 NEU-DET, 1,400 Severstal), and 13 of 15 correct on a held-out suite of synthetic negatives. It is not wired into this static page — the page will happily score a photograph of a cat and tell you it found crazing. reports/ood_guard.json, reports/ood_guard.md

The confidence in the table is a probability, and that took work

A YOLO class score is not a probability. On the held-out test split the raw scores carry an expected calibration error of 0.1418 — a box shown at “0.40” was right far less often than 40% of the time. An operator who is told 0.40 and means 0.40 will make different decisions from one who is told a number that happens to be 0.40.

Chosen out of fold, not by eye

Five candidates were fitted under 5-fold cross-validation on the validation split, grouped by source image so no crop leaks between folds. Out-of-fold ECE: isotonic 0.0250, platt 0.0614, temperature 0.0961, identity 0.1008. Isotonic won on data it had not seen, which is why its in-sample expressiveness is not an argument against it.

It cannot reorder anything

The map is monotone, so it cannot change which detection outranks which, and mAP50 is numerically unchanged at 0.707986 before and after — the same quantity computed twice under two rankings, which is what makes the invariance meaningful. Isotonic regression is only non-decreasing, though, and would collapse runs of distinct scores onto one plateau value; a vanishing 1e−06 term restores a strict order without moving any calibrated value by more than that.

Limitations

Written to be believed rather than to be reassuring. If one of these is a blocker for your line, it is better read here than discovered later.

This is carbon steel, not stainless

NEU-DET is 1,800 grayscale 200×200 images of hot-rolled carbon steel. Nothing on this page has been measured on stainless, and the metallurgy of the surface is not the same. Every number here is a capability demonstration on a public benchmark, not a prediction of performance on Jindal stainless strip.

One lighting rig, one camera

The whole dataset was photographed under a single imaging setup. Nothing has been measured on a different camera, a different illumination geometry, or a different upstream mill — and the vision vendors themselves say the same defect class looks different from different mills. The cross-domain section above is what happens when you ignore this: AUC 0.608, which is chance. The per-line calibration protocol, not the architecture, is what decides whether this works.

Roll marks are measured weak

On GC10-DET, the roll-mark family (rolled_pit, crease) scores mean AP50 0.203 on 24 test instances. Four of eleven live rolled_pit images produce zero detections at conf 0.15. With 24 instances one flip moves recall 8–9 points, so that number is soft in both directions. Overall GC10 held-out test is mAP50 0.5821 — materially below the NEU-DET figure, on 333 images and 530 boxes. reports/gc10_coverage.json → brief_relevant_families.roll_marks, test_evaluation.overall

Edge cracks are covered only by a proxy

No public dataset has an edge-crack class. The edge family here is crescent gap and waist fold — AP50 0.880 on 61 test instances, which is a strong result for edge geometry and not evidence about cracks. Calling it edge-crack detection would be a lie, so it is not called that. reports/gc10_coverage.json → brief_relevant_families.edge_defects_proxy; reports/gc10_dataset.md

Crazing recall is 0.224

The weakest class on the weakest axis. 53 of 68 crazing misses are blind misses, not mislocalised ones. If crazing is the defect that costs you money, this model is not yet the answer for it, and the section above explains why rather than averaging it away.

Three different false-alarm numbers, not one

The NEU-DET clean-crop proxy reads ≤23.7% (95% CI [17.7%, 30.1%]) but its effective sample size is 179 of 771 crops, and it ranges 5.8%–48.8% by source class. A legacy definition of the same thing reads 59.4%. The real clean-steel measurement — 93.7% before the fix, 32.5% after — is the one to trust, and it is much worse than the proxy suggested. reports/false_alarm.json; reports/gap1_cross_domain.json

The cost model is an assumption

Defect prevalence at 5% of frames and the miss-to-false-alarm price at 12:1 are assumptions, not measurements, and only their product is identifiable. conf 0.15 is set by a 90% detection floor, not by the economics. Every rupee figure in the deck is arithmetic on a swept assumption with the inputs printed beside it — a shape, not a forecast.

What this page in particular does not do

It runs the six-class NEU-DET head, not the better 10-class joint checkpoint, so the cross-domain false alarms above are live here. It has no out-of-scope gate, so it will score a photograph of anything — that gate is vendor/ood_guard.py in the Python console and it has not been ported. Its tiled path over a non-square frame has no Python reference: ultralytics was run on the twelve square NEU-DET frames, so the parity tables above cover the single-pass path only, and the strip results are a browser-against-Node comparison rather than a check against ultralytics. The two strip frames are GC10-DET captures whose real defects — a roll mark and a weld line — are not classes this six-class head has, so what it returns on them is the nearest class it owns, not a correct name. And it runs single-threaded WASM on your CPU, so its timing is not the deployment timing. site/verify/strip_check.json; site/verify/parity_browser.json → out_of_domain

Not measured, and not claimed

Training-seed variance: three seeds per architecture is about 6.5 h on this machine and would upgrade the nano-versus-small finding from “these weights” to “this architecture”. Transfer across magnification: the accuracy curve was measured on 200×200 crops, and a 320 px tile at 0.2 mm/px covers 64 mm of strip. The unsupervised anomaly channel and the closed loop back to the mill are proposed, not built.

The console

There are two of them. One is this page, and it is running. The other is a Python console that does the things a browser tab should not be asked to do. Neither is a mock-up of the other.

This page is the inspection station

Not a description of one, and not a trailer for the Python build. The 12.1 MB yolov8n_neudet_best.onnx you downloaded a few sections ago is the shipped export of the shipped checkpoint. The resize, the NCHW packing, the decode, the class-aware NMS and the isotonic calibration all come from site/js/detect.js, site/js/tiling.js and site/js/calibration.js — and those same three files are what site/verify runs under onnxruntime-node and under headless Chrome to check this page against Python ultralytics, detection for detection. Both tables in the verification section above are that comparison.

It is not a thin demo. Full-width strip frames are cut into square windows and merged with one global NMS rather than squashed into the square input. Confidences are the calibrated probabilities, not the raw head scores. Severity is scored with the same tier-times-confidence-times-area rule the Python path uses, and every detection carries the operator action for its defect class. The confidence slider re-decodes from the cached output tensors, so it moves the threshold the model was actually thresholded at.

Running in the tab is the point, not the compromise

Strip imagery is process data. A mill that will not send coil photographs to a vendor cloud has a real objection, and this architecture answers it structurally rather than contractually: no frame leaves the machine. The image is read into a canvas, turned into a tensor and discarded. There is no upload, no inference endpoint, no bucket, no retention policy to negotiate.

What follows from that is not marketing. There is no cloud dependency, so a WAN outage does not stop inspection. There is no per-inference cost and no autoscaling bill. There is no cold start — the session is warmed once and the model stays resident. And the artefact is portable in the way that matters: a single ONNX file and a WASM runtime that needs no GPU, no CUDA and no Python. The same file that ran in this tab is the file an industrial PC on the mill floor would load through onnxruntime, which is the version of this that would actually be deployed.

To be precise about the claim: the browser is how deployability is demonstrated here, not a proposal to run production quality control as a web page. It is the same weights and the same arithmetic on a runtime anyone can audit by opening dev tools — and single-threaded WASM on a laptop is a lower bound on the hardware, not the deployment target.

What the Python console adds over this page

Four things, and they are the four this page genuinely should not do. They are why the console exists rather than being folded into the tab.

Batch scoring and the coil report

Many frames through predict_batch, a sortable frame table, then coil-level disposition against the HOLD and DOWNGRADE rules and a downloadable coil report from vendor/report.py. A coil verdict is an aggregate over hundreds of frames; one frame at a time cannot produce one.

EigenCAM attention maps

An Explain button runs a second instrumented forward pass through vendor/explain.py and renders where the layer's features responded, with an occlusion-sensitivity fallback when the CAM degenerates. It needs the PyTorch graph, not the frozen ONNX export this page carries, so it cannot run here at all.

Line simulation

N frames scored one at a time to show per-frame latency, the frame rate a strip at a given speed implies, and how many accelerators a full-width line would need. It is the capacity argument, and it needs a controlled sequential run rather than a click.

The out-of-scope gate

vendor/ood_guard.py runs first in the console: a six-class defect head has no “not steel” class, so a frame the gate rejects gets a withheld verdict instead of a confident wrong answer. This page has no such gate and will happily score a photograph of anything — the limitation is listed above because it is real.
